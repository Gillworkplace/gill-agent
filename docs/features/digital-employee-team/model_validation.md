## 发现及修复

这些问题如实保留，不将第一次试跑写成全程无干预通过：

1. 上级将原问题继续升级后，其评估任务没有同步阻断。现场先由测试管理者阻断避免多余调用；修复领域转换，升级者进入blocked，明确答复后评估任务completed，原任务queued。新增先失败后通过的回归测试。
2. 模型为新产物自行填写了ID，服务端正确拒绝，但 Worker 只暴露笼统HTTP404，模型无法判断是无效引用。补充工具参数说明：新建省略id，更新仅用真实ID/revision；Worker 保留服务端错误详情和HTTP类型，失租判断仍有效。
3. 组合检索词被当成一整段连续文本，可能导致已有授权源查询无匹配；模型容易误解为未挂载。改为在当前已授权源内按词匹配排序，增加authorizedSourceCount及matched/no_matches/no_mounted_sources，未扩大读取范围。
4. 引用回复即使显式mentions=[]仍会自动唤醒原发送人，可能意外再派任务。现在显式空列表仅通知；未提供mentions时才沿用原回复默认行为。新增定向投递回归测试。
5. 明确追加资源并恢复后，将该运行的上限提醒标记为已响应；与其他任务有关的未知动作提醒仍保留，避免完成后残留已处理的预算@我。新增隔离回归测试。
6. 模板生成重试会保留上一次草稿error，可能在资源恢复后仍展示旧429。重试开始及新草稿成功时清理当前草稿错误，原job/action失败历史保留；新增回归测试。

回归：Java21领域19项、独立PostgreSQL测试4项、项目虚拟环境Python15项通过；前端代码未改动，沿用已通过的4项状态测试、类型检查与桌面/手机验证，生产镜像重新构建。

## 上限和环境故障

试跑达到配置的18次模型派发上限后停止新派发，保留已有最终分析稿与核查记录；测试管理者明确追加6次调用及10分钟，并恢复原检查点。上限并非所有调用均成功，用量按供应商实际回执记录，不估算未报告的用量或货币费用。

恢复中 Docker 的59GB虚拟盘耗尽，PostgreSQL因写入失败退出。清理约15.08GB可重建的无用构建缓存，未删除数据库/文件库/其他业务卷；PG完成WAL恢复，虚拟盘重新有约16GB空间，主站及真实认证恢复。中断工作保留动作与检查点，不能将当时的HTTP/数据库异常解释为模型资源再次不足。
