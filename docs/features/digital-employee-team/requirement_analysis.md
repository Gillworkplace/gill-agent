## 1. 背景与目标

### 1.1 业务背景

用户希望通过一个平台组织数字员工承担专业工作。员工由平台根据 Prompt 生成和配置，员工之间有上下级及监督关系；管理者通过 Prompt 定义协作流程，由大模型结合目标、上下文和实际结果控制执行。

最初讨论从产品、系统设计、开发、测试团队出发，随后用户明确：平台是通用团队平台，后续还包括业务团队；设计必须保留模型灵活度，不限制员工能力，不局限场景；当前先搭好基础设施。研发是明确的应用示例，不能成为平台对象、员工能力或流程执行的硬边界。

### 1.2 已确认的来源与功能目标

| 来源 | 用户明确的内容 | 需求含义 |
| --- | --- | --- |
| D18 | 平台通过 Prompt 生成与配置数字员工；Prompt 定义流程，大模型控制团队运行，员工相互监督 | 提供员工、团队、流程与真实执行的管理能力 |
| D19 | 员工拿不准方案向上级提交，上级仍无法解决继续向上，最终反馈用户 | 支持可追溯的逐级评估与用户决定 |
| D20 | 新增员工或修改员工、团队流程的 Prompt，所有调整由用户决定，员工只能建议 | 用户掌握组织与指令基线的变更权；建议与生效分开 |
| D21 | 支持已有项目改造和新项目开发 | 研发应用应能表达现有基线和空白起点，不能仅能演示从零生成 |
| D22 | 保留模型灵活度，不限制员工能力，不局限场景 | 岗位、场景、流程步骤、产物类型均开放；模型可自主选择方法、计划和协作方式 |
| D23 | 通用团队平台后续有业务团队，只需先搭基础设施 | 当前建设通用执行与管理底座；研发和业务团队通过配置承载，不内置为两套行业应用 |

需要实现的基础闭环：用户表达目标 → 平台生成员工并配置团队 → 用 Prompt 定义协作规则 → 模型组织工作与沟通 → 实际执行并形成产物 → 员工监督、修正与逐级升级 → 用户管理运行并查看交付。

### 1.3 本期范围与非目标

本期基础设施包含：员工生成和版本管理、团队及上下级配置、开放工作目标与上下文、Prompt 流程、模型驱动的任务安排与通信、工具执行、交付物与监督、升级与用户决定、运行观察、控制和恢复。

范围边界：

- 提供可配置的通用平台，不把完整研发管理系统、CRM、销售或其他业务应用作为本次必须内置的产品。
- 岗位模板、团队示例和行业示例用于上手与验收，不构成员工能力上限；用户定义新岗位或新工作无需修改平台业务代码或登记场景枚举。
- 本期不确定新框架、重写技术栈、生产发布或外部业务系统的具体接入清单。现有技术栈与可用执行环境先作为评估基础。
- 本文交付需求分析，不以生成员工介绍、聊天记录或流程图冒充基础设施已经运行。
- 保留用户已有产品与资料；具体旧页面、CLI、协作功能如何迁移，在开放事项中单独决定，不随新定位直接删除。

### 1.4 术语与灵活度边界

| 术语 | 含义与要求 |
| --- | --- |
| 数字员工定义 | 稳定身份及用户决定的工作指令；职责用于组织工作和表达偏好，不是平台按岗位设置的能力白名单 |
| 团队席位 | 某个员工定义在某团队承担的身份、责任和关系；与一次实际执行实例区别 |
| 员工运行实例 | 某次运行中使用既有员工定义的执行上下文；模型调用、执行尝试或实例不是新增员工定义 |
| 组织关系 | 上下级用于处理拿不准的问题；监督关系用于检查工作，两者可分别表达，不能由岗位名称推断 |
| 流程 Prompt | 用户决定的协作要求与原则；可以描述顺序、检查或其他约定，平台不要求转换成固定业务阶段图 |
| 运行计划 | 模型依据现场情况形成、调整的任务、分工和方法；在有效指令内重规划，不等于修改流程 Prompt |
| 交付物 | 任意工作成果，可为文字、表格、代码、图像、资料、报告或外部结果的引用，不限定软件文件 |
| 验证事实 | 实际观察或执行的结果；与员工判断、管理者接受决定分开记录 |

员工可以在可用环境中选择工具、编写辅助脚本、组合方法、查找资料、请求其他员工协助和调整任务计划。平台不因其岗位或团队类型预先拒绝这类方法。实际工具和外部资源是否可达必须如实反馈；写入员工长期 Prompt 或团队流程的调整仍遵守 D20。

## 2. 用户与场景

### 2.1 角色

| 角色 | 责任与边界 |
| --- | --- |
| 管理者（人类用户） | 提出目标，决定员工与规则调整，查看运行、主动介入、处理逐级升级到自己的事项 |
| 数字员工 | 按有效指令工作、沟通、交付、检查与提出建议；拿不准时向其上级提交评估 |
| 上级员工 | 评估下级的问题；能解决则提供意见，仍无法解决继续升级。上级身份不自动取得改写组织规则或用户目标的权限 |
| 监督员工 | 依据约定检查具体工作与产物，提出问题并参与复核；不因发出监督意见自动成为对方上级 |
| 平台 | 提供模型上下文、协作执行、事实记录和控制入口，不预设某个岗位必须具备或不得具备什么业务能力 |

### 2.2 用户故事

| 编号 | 用户故事 | 可观察结果 |
| --- | --- | --- |
| SC-01 | 作为管理者，我希望描述需要什么员工，让平台生成其工作指令，以便自行组成不同团队 | 员工内容可查看、修改、保存与投入实际运行；生成失败或能力依赖缺失可见 |
| SC-02 | 作为管理者，我希望表达组织层级和协作流程，以便让模型组织团队完成开放的工作目标 | 团队关系、有效 Prompt 和运行版本可查看，岗位与工作步骤可变化 |
| SC-03 | 作为管理者，我希望员工自主分工、沟通和选择方法，以便减少逐项派单 | 模型的任务安排与实际工作可追溯，必要时能重规划和交接 |
| SC-04 | 作为员工，我希望检查彼此产物并纠正问题，以便使监督影响实际交付 | 问题、修正与复核对应明确产物与版本，不仅是一条评论 |
| SC-05 | 作为拿不准方案的员工，我希望上级逐级评估，以便团队内部先处理无法确定的问题 | 上级能解决、需继续升级、最终需用户决定的路径均可运行 |
| SC-06 | 作为管理者，我希望暂停、查看、提出变更并继续运行，以便管理长期工作 | 能识别在途、已完成与结果未知的动作；组织变更不静默混用新旧规则 |
| SC-07 | 作为管理者，我希望同一基础设施既能承载研发团队，也能承载业务团队，以便持续扩展用途 | 不改平台业务代码即可配置两类任务；无代码仓库的工作同样可以运行和交付 |

## 3. 功能需求

DET-01～DET-09 延续探索稿的含义；新增条目顺延。下列描述的是需要具备的行为，不代表相关技术方案已批准。各段的细化建议与未决政策见 §8。

### 3.1 DET-01 员工生成、配置和复用

- **输入**：用户自然语言要求、可选参考资料和已有员工；岗位名称与专业领域为开放文本。
- **处理**：模型生成可阅读的员工定义，包含工作 Prompt、责任、输入需求、交付要求、协作约定和能力依赖说明。用户可以进一步通过 Prompt 或编辑方式调整。
- **输出**：持久化员工定义、版本和来源；能查看变化、在团队中复用或停用，历史运行引用不被破坏。
- **分支**：生成失败保留用户输入并提供继续修改入口；描述有歧义时提出具体问题；所需工具不可用时说明依赖，不假称已经具备或执行成功。
- 生成与编辑由用户明确指令触发。员工建议生成的新员工或修改内容必须作为建议呈现，不直接进入生效团队。

### 3.2 DET-02 团队、层级和协作关系

- **输入**：用户的团队要求、员工定义版本、责任和关系描述。
- **处理**：支持可变员工数量、开放岗位、上下级与监督关系；这些关系可由平台根据用户输入生成草案，并由用户决定配置。岗位名称本身不产生组织权限。
- **输出**：可查看的团队与关系配置及版本，能够定位员工当前的上级和监督职责。
- **分支**：缺失、矛盾、自指或循环的升级关系必须可识别，不能在实际升级时丢失问题或编造上级；具体关系形式与配置异常处理在 Q-03 细化。
- 上下级的有效升级路径应最终能反馈用户；监督可以相互进行，不将管理层级的无环要求误用于禁止相互监督。

### 3.3 DET-03 通过 Prompt 定义协作流程

- **输入**：开放自然语言的流程要求、目标、约定和可选参考资料。
- **处理**：保留原始 Prompt 与有效工作指令，展示必要的解释和待澄清内容；不要求用户编写流程代码，不固定岗位清单、阶段、轮流发言顺序或业务场景。
- **输出**：有版本的流程定义，可用于不同团队和不同工作目标。
- **分支**：规则冲突或含糊时明确指出，保留用户输入并支持修订；解释摘要不能无记录地替换用户规则。
- 用户可以规定严格顺序，也可以仅描述目标、责任和检查原则。平台应保留模型在这些规则内选择路线、补充步骤、并行安排和重规划的空间。

### 3.4 DET-04 模型驱动的运行与动态任务安排

- **输入**：工作目标、团队和流程版本、已有产物、上下文、通信、执行反馈及用户指令。
- **处理**：模型决定后续任务、执行员工、沟通对象、方法、工具、交接、评估与返工。平台执行对应动作并反馈真实结果，支持多轮持续推进。
- **输出**：任务、责任员工、依赖、决策依据摘要、实际动作及结果，能在界面中直接查看。
- 每次运行应能明确最终接收升级事项的人类管理者，不能仅靠空间成员列表或员工自由选择猜测；模型调用和员工消息不改变该绑定。
- **分支**：员工或工具不存在、上下文不足、动作失败或结果未知时，返回可供模型继续判断的实际状态；拿不准的方案进入 DET-09。
- 模型可以动态新增子任务和为既有员工建立执行实例；不能借此创建未经用户决定的新员工身份或改写员工与流程 Prompt。
- 需要实际执行的任务不能仅凭模型文本宣布执行成功；纯分析任务可用持久化分析产物验收，不机械要求每种任务必须调用外部工具。

### 3.5 DET-10 员工沟通、交接和上下文

- **输入**：员工或用户发送的消息、目标接收者、关联任务、问题和资料引用。
- **处理**：支持员工之间及上下级之间的沟通、工作交接、请求协助和补充上下文，能区分人类用户、员工实例和系统来源。
- **输出**：有发送者、接收者、关联对象和时间的通信记录；接收和处理结果可追溯。
- **分支**：无法投递、重复投递、接收者不可用或消息尚未处理时状态可见；不以“发送了消息”替代“完成了交接”或“对方已决定”。
- 员工不能通过伪造用户来源的消息取得变更规则的权限；普通员工消息仍可提供事实、建议和协作输入。

### 3.6 DET-11 开放工具与实际执行

- **输入**：模型选择的动作、参数、关联任务及可用环境。
- **处理**：提供通用执行入口与可扩展的工具/Skill/MCP 接入，支持查询、文件、脚本、浏览器及后续能力；工具可发现、组合和扩展，岗位不是工具执行白名单。
- **输出**：实际执行的身份、输入、开始和结束情况、结果、错误及证据引用；可区分未执行、进行中、成功、失败、取消和结果未知。
- **分支**：外部系统、凭据或资源不可用时保留失败及下一步，不伪造业务结果；存在副作用但结果未知的动作先核实，再判断如何继续，避免直接重复执行。
- 具体工具连接依赖实际环境和用户提供的访问条件。平台接口和执行协议应允许新增工具，无需为每个行业改写调度主流程。

### 3.7 DET-05 产物监督、问题修正与复核

- **输入**：任意类型的交付物版本、检查要求、可获得的证据和员工意见。
- **处理**：支持检查、提出问题、安排修正及针对新结果复核。模型依据有效流程安排检查时点与对象；不固定所有工作都必须经过同一套审批。
- **输出**：检查对象、版本、依据、结论、问题、责任和处理记录；“提出问题”“已修正”“复核通过”和“接受结果”分别识别。
- **分支**：员工相互认可而实际验证失败时保留失败；证据不足时明确未验证或无法判断；更换产物版本后进行影响判断，旧评审不自动覆盖新版本。
- 监督的阻断、解除和改派权限需要由有效规则明确，尚未决定的全局默认政策保留 Q-01；上级评估和用户接受均不能把失败事实改写成成功。

### 3.8 DET-09 拿不准方案时逐级升级

- **输入**：员工提出的具体问题、不确定原因、相关资料、产物、已有尝试和候选方案。
- **处理**：按上下级关系提交评估；上级能解决则记录意见，上级仍无法解决继续向上，最终反馈用户。支持上级补充核查或请求资料。
- **输出**：当前处理者、已经过的层级、各级评估、剩余问题及最终决定来源；用户能够看到需要自己回答的事项及完整必要背景。
- **分支**：无人答复、反复转交、回答仍含糊或层级配置异常不能被视为问题已经解决；等待与恢复细节见 Q-02/Q-03。
- 接到处理意见后，应能关联决定、适用范围与后续任务，保留复核机会。该能力不产生阶段全审批，也不扩大上级的组织修改权。

### 3.9 DET-06 运行观察、干预、暂停与恢复

- **输入**：用户的查看、补充指令、暂停、恢复或终止请求，以及服务中断后的状态。
- **处理**：展示团队当前目标、员工活动、任务与依赖、通信、产物、监督、升级和资源使用；处理控制请求并返回实际状态。
- **输出**：可恢复的运行记录，以及已完成、未执行、在途和结果未知的事项；控制请求已接收与控制动作已生效分别可辨。
- **分支**：在途工具无法立即取消、服务重启、连接重建和消息重复时保留状态与已有成果；恢复先核实未知结果，不盲目重做。
- 不在需求中默认等待期间全团队停止或其他工作继续。平台需支持表达等待范围与依赖，具体政策在 Q-02 明确。

### 3.10 DET-07 通用交付与结果判断

- **输入**：目标、完成要求、实际产物、验证、监督结论、缺陷及待决定事项。
- **处理**：模型整理交付结果；平台将总结与实际产物、执行和检查记录关联。
- **输出**：可以取得的成果、覆盖情况、依据、未验证内容、未解决问题和后续建议。
- **分支**：缺少所要求产物，或动作尚未完成、失败、未验证，不能将相应内容显示为已验证成功。整体交付是否满足目标，依据该次工作的有效要求和规则判断；遗留问题持续披露，不默认任意未关闭问题都阻断全部交付。
- 执行结束、验证通过、用户接受、外部发布为不同事实。不同团队可有不同完成要求，不以“代码构建通过”作为所有团队统一的交付条件。

### 3.11 DET-08 版本、变更影响与历史追溯

- **输入**：员工、组织、流程、目标、产物和评审的版本以及运行中变更。
- **处理**：识别每次工作实际采用的版本；变更展示前后内容和影响，记录生效依据与适用范围，保留历史引用。
- **输出**：可定位的有效指令、当前版本、历史决定和受影响任务；历史结论不会随“当前版本”指针变化而被改写。
- **分支**：用户请求基于过期版本变更时指出冲突；运行中修改是否立即生效或仅对后续运行生效，见 Q-04，不静默混用规则。

### 3.12 DET-12 用户决定员工与规则调整

- **输入**：用户明确的新增员工或调整员工、团队流程 Prompt 的指令，或员工提出的变更建议。
- **处理**：员工建议可包含候选内容和理由，但与生效配置分开。只有用户的明确创建、调整或接受决定可以使相关组织或指令变更生效。
- **输出**：建议、用户决定、变更内容、来源、版本及生效记录。
- **分支**：建议被拒绝或未回复时不生效；员工通过工具、消息、知识记录或其他途径绕过用户决定修改有效规则，应被识别并保留记录。
- 用户通过 Prompt 或界面直接发起明确操作，本身可作为该项决定依据，不增设无意义的重复确认。运行实例、任务分派、执行方法与辅助脚本不一律当作组织规则变更；将其写入长期员工/团队流程 Prompt 时适用本条。

### 3.13 DET-13 通用工作目标与基础管理界面

- **输入**：用户开放的目标、资料、约束和期望成果；可选现有工作基线。
- **处理**：提供员工、团队与关系、Prompt 流程、工作目标、运行观察及用户待办的管理入口。主要信息可通过对象视图查看，不依赖读完所有聊天才能理解进度。
- **输出**：可管理的工作目标与资料引用、运行和交付记录。代码仓库、软件版本、业务系统记录都可作为上下文，均不是所有工作的必填前提。
- **分支**：输入缺失时指出具体需要什么；既有资料与模型生成内容的来源可辨。研发示例支持现有代码变更和空白起点，业务示例可以无代码仓库运行。

## 4. 数据模型

本节给出需要保存的业务事实；详细字段、类型、约束与关系见[候选附录](infrastructure_contract_candidates.md)。这些是系统设计输入，不是已经批准的 DDL。

| 实体组 | 必须表达的事实 | 关键约束 |
| --- | --- | --- |
| 员工与员工版本 | 稳定身份、生成来源、工作 Prompt、职责和修订 | 员工定义、团队席位与运行实例分别识别；职责与能力描述不变成岗位白名单 |
| 团队、席位及关系 | 组成、责任、上下级、监督及对应版本 | 管理关系和监督关系分开；升级能找到明确处理者，配置异常可见 |
| 通用目标与上下文 | 用户目标、资料、约束、期望成果及可选已有基线 | 不强制代码仓库或行业类型；来源和版本可追溯 |
| Prompt 流程与版本 | 原始指令、有效指令、解释和变更来源 | 指令变更与模型日常重规划分开；模型解释不静默替代原指令 |
| 运行、实例与任务 | 采用版本、员工上下文、责任、依赖、等待和实际状态 | 业务任务类型开放；技术生命周期不固化业务阶段 |
| 通信与交接 | 发送者、接收者、对象、关联任务和处理结果 | 用户、员工、系统来源不可混淆；发送、接收、决定分别记录 |
| 执行与证据 | 动作、输入、结果、外部状态、关联标识与原始输出 | 结果未知单独识别；实际验证与模型判断分开 |
| 产物、监督与问题 | 任意成果版本、检查依据、缺陷、修正与复核 | 评审绑定明确版本，保留失败和未验证事实 |
| 升级与评估 | 问题、各级处理人、路径、意见及用户决定 | 无答复不是许可或解决；保留完整升级链 |
| 变更建议与决定 | 候选变更、发起人、用户决定、生效版本与范围 | 员工仅建议；不能将建议直接写为生效配置 |
| 运行事件与用量 | 排序、关联、状态变化、模型调用和资源记录 | 支持查询与恢复，不以易丢失的聊天或实时通知作为唯一事实源 |

存储评估先沿用现有 PostgreSQL、Redis 与 MinIO：持久业务事实与版本、通知和任务分发、产物与原始证据内容分别评估。具体表、索引、Redis key、事务与一致性机制交系统设计师确定，禁止用新需求直接宣称现有实现已满足可靠恢复。

## 7. 约束与非功能需求

### 7.1 可验证的通用约束

| 编号 | 要求 | 验证方式与责任 |
| --- | --- | --- |
| N-01 模型灵活度 | 任意岗位、工作目标、任务内容、产物和业务场景可表达；用户规定的严格流程也可表达。平台不按岗位预置能力白名单，不将模型调度降为固定四阶段 | 用研发与非研发两套配置，核对无需修改平台业务代码；产品与测试验收 |
| N-02 指令生效 | 员工、团队与流程的实际有效指令能进入对应模型请求，来源和版本可核对；执行结果可追溯至所用指令 | 开发验证请求契约，测试验证场景行为；不能只检查保存接口或固定全文回复 |
| N-03 状态与证据 | 员工判断、任务状态、外部动作结果、验证事实和用户决定分开；未执行、失败、未知、未验证不能改写为已验证成功 | 检查故意失败、未知结果和缺证据样例，核对界面与事实源一致 |
| N-04 归属与身份 | 继续使用现有用户/空间隔离；员工与系统有可辨执行身份。员工来源的建议、消息或调用不能变成人类用户的组织变更决定 | 对跨空间访问与员工直接应用规则变更进行验证，保留有效用户操作的正常路径 |
| N-05 幂等与并发 | 重复请求、重复任务投递、重复决定和过期版本修改不会无声地产生重复副作用或覆盖新内容 | 重复相同请求、并发修改和消息重投；过期/内容冲突可见，作用域由接口设计明确 |
| N-06 可靠运行 | 断连、服务重启、模型调用失败后能查询既有任务、执行与决定事实；控制入口在员工执行期间可响应 | 中断前后对照任务、事件和产物；验证暂停/查询不被执行循环等待锁死 |
| N-07 恢复与未知结果 | 结果未知的外部动作先核实再决定继续或重试；已完成成果和历史失败不因恢复丢失 | 在动作发生后、回执前制造中断，检查补查、关联和副作用情况 |
| N-08 资源与性能 | 员工定义数量、运行实例、模型并发和执行环境数量分别评估；不把现有沙箱会话容量直接当作团队员工人数上限 | 系统设计师给出实际环境下的并发、事件负载、控制响应与资源指标，测试按该基线执行；见 Q-05 |
| N-09 运行限制 | 模型与执行资源使用可观察；资源耗尽、依赖不可达或持续无进展有真实状态和处理出口，不靠无限互评掩盖阻塞 | 使用可配置运行条件验证；不在本需求中预设统一的员工数、信心分数、返工次数或业务超时 |
| N-10 可维护与兼容 | 保留现有技术栈及模块依赖规范，角色/场景扩展不要求修改业务内核；旧能力迁移有兼容说明 | 架构评审、变更清单与影响回归；不直接按新定位删除现有数据或能力 |

必要的参数长度、分页、资源配额和执行超时由系统设计师依据实际环境细化；这些是可运行基础设施的资源约束，不得替代为固定岗位能力或场景限制。

### 7.2 错误与用户反馈语义

以下为错误分类和代码候选，供接口设计定稿；不是现有接口已提供这些响应。错误结构沿用 `{"error":{"code":"...","message":"..."}}`，并关联可查询的运行、任务或操作。

| 候选代码 | 触发条件 | 用户或模型可观察的处理 |
| --- | --- | --- |
| TEAM-4001 | 组织配置缺失、冲突或升级关系不可解析 | 指明对象、冲突和影响；保留草案/问题，提供修正入口，不能伪造上级 |
| RULE-4031 | 员工试图直接应用需要用户决定的员工/指令变更 | 保留建议能力，拒绝生效并说明需用户决定；不把正常任务重规划误判成此错误 |
| REV-4091 | 写入基于过期版本或同幂等键内容冲突 | 返回冲突基线，允许获取最新版本后重新表达变更，不静默覆盖 |
| RUN-4091 | 控制或状态变更与当前事实不相符 | 返回当前状态和在途动作；重复操作按已确定语义返回，不伪报已停止 |
| EXEC-5021 | 模型服务、工具或外部依赖执行失败 | 记录实际失败和影响，反馈可供模型判断的结果；拿不准则逐级升级 |
| ESC-4091 | 评估或用户决定基于过期升级状态 | 展示当前处理者与有效评估，不重复应用旧决定 |

动作结果未知是独立执行状态，不等于客户端应自动重试的普通报错。查询动作本身成功时仍可返回未知状态、已经取得的证据和需要核实的事项。

| 方案 | 可取之处 | 主要代价与需验证之处 |
| --- | --- | --- |
| A：在现有共享会话上增加员工身份、指令与协作状态 | 可复用现有消息、界面和执行代码 | 需证明不会继续把团队等同单会话/单沙箱/单任务锁；版本、任务、通信、升级和恢复仍需完整事实模型 |
| B：明确通用团队运行对象，复用现有单次模型与工具执行能力 | 能分别表达团队配置、运行实例、动态计划、任务、监督和升级，并跨研发/业务使用 | 新增运行管理和迁移工作；现有执行器、总线、Prompt 传递与恢复不能直接视为满足要求 |

产品建议优先围绕 B 明确对象和行为，保留模型动态控制。最终模块边界、复用方式、并行与恢复实现由系统设计师评估；不在本分析中选择新的 Agent 框架、数据库或消息系统。

### 9.2 必须保持的设计方向

- 组织配置与运行计划分开：模型能灵活工作，用户仍决定员工和长期指令变化。
- 流程规则与真实状态分开：Prompt 表达规则，实际任务、产物、执行、监督和决定有可核查事实。
- 岗位和领域不进入封闭业务枚举：研发、销售、运营或混合团队均为配置实例。
- 扩展能力与运行内核分开：新增工具与工作类型不要求重写一套行业调度器。
- 共同生命周期与业务阶段分开：可以有运行/等待/结束等基础设施状态，不能据此强制所有团队遵循相同业务步骤。

## 10. 里程碑与任务拆分预览

以下为候选工作顺序，尚未形成接口级开发任务；不将此列表视为已获架构批准或已经完成。

- [ ] M1：关闭适用的业务规则缺口，完成基础设施架构、执行身份和恢复设计。
- [ ] M2：实现员工/团队/流程/目标定义、版本及用户决定的变更机制。
- [ ] M3：实现平台生成员工、关系配置、Prompt 流程与基础管理界面。
- [ ] M4：实现通用上下文、工具执行、产物和实际结果记录。
- [ ] M5：实现模型驱动的动态任务、通信、协作与交接。
- [ ] M6：实现监督、问题修正、复核、逐级升级及用户待办闭环。
- [ ] M7：实现运行观察、控制、事件补取、中断恢复与幂等处理。
- [ ] M8：在同一基础设施验证研发和业务配置、真实执行与重要失败路径，完成独立测试与产品验收。

下一阶段在有效需求和架构明确后，使用子任务拆分流程形成接口、函数、依赖与整合安排。本次不直接生成未经设计评审的可开工任务。

## 11. 竞品对比与产品优势

已有[公开资料调研与证据](product_proposal.md#3-竞品对比与产品优势)保留为调研记录：CrewAI、AutoGen 和 ChatDev 的官方资料在同一需求讨论中核对，未部署实测。本文不复制另一套竞品事实基线，不把“有多员工”“有管理者”单独宣称为优势。

本次产品方向补充为可检验的通用基础设施价值：

| 假设 | 预期用户收益 | 比较和验证方式 | 当前状态 |
| --- | --- | --- | --- |
| V-01 Prompt 生成、配置与运行一体化 | 用户能在同一平台组织员工并查看实际工作，减少手工拼接配置和派单 | 对相同目标记录配置修订、人工派单、上下文补充和可用交付；不预设效率提升比例 | 设计假设，未实现、未验证 |
| V-02 保留模型的开放工作能力 | 研发和业务团队可共用同一底座，不需为新岗位或场景改内核 | 用不同岗位与两类工作配置验证，检查是否出现行业枚举、固定阶段或角色工具限制 | 用户明确的产品要求，实际效果未验证 |
| V-03 监督与逐级升级形成实际闭环 | 团队能发现并修正问题，上级先评估，用户处理最终仍无法确定的事项 | 在带已知缺口、冲突和真实执行失败的任务中检查发现、升级、修正及复核表现 | 设计假设，不能承诺绝对正确 |
| V-04 可追溯的控制与恢复 | 用户知道团队为何继续、等待、返工或结束，长期工作可继续管理 | 对规则变更、版本替换和执行中断检查遗漏、重复副作用和人工补充负担 | 设计假设，需承担状态和版本维护成本 |

资料说明竞品具有相关能力，不代表本方案已具备竞争优势。能力数量、模型自评、生成文本量或单次成功演示都不单独证明收益。

### 12.3 程序验证、模型质量与业务验收

开发验证请求参数、Prompt/工具接入、状态变更、版本、身份与幂等契约；测试独立验证用户场景、真实前后端与执行链路、失败恢复及模型质量；产品依据目标和实际证据作业务验收。

模型质量需覆盖职责含糊、事实冲突、工具失败、能力依赖缺失、员工分歧和应升级但未识别的不确定问题。既要检查“已提出的不确定问题能否上报”，也要检查是否存在错误自信、隐藏失败或重复互评空转。测试方法、样例与通过口径需在规则和架构明确后形成，不能以模型自评或一次满意回答证明稳定质量。
