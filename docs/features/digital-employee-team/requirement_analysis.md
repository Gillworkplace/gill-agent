## 1. 背景与目标

### 1.1 业务背景

用户希望通过一个平台组织数字员工承担专业工作。员工由平台根据 Prompt 生成和配置，员工之间有上下级及监督关系；管理者通过 Prompt 定义协作流程，由大模型结合目标、上下文和实际结果控制执行。

最初讨论从产品、系统设计、开发、测试团队出发，随后用户明确：平台是通用团队平台，后续还包括业务团队；设计必须保留模型灵活度，不限制员工能力，不局限场景；当前先搭好基础设施。研发是明确的应用示例，不能成为平台对象、员工能力或流程执行的硬边界。

用户在原型评审中进一步要求简化：概览就是不同团队的群聊，查看团队进展和空闲程度，通过 @我 处理事项；数字员工入口管理模板及能力 Skills，团队入口展示本团队的实际员工。同一个实际员工只能属于一个团队，可复用的是模板，而非同一员工身份。此次取消独立运行记录和我的待办顶级界面，不取消运行、证据、监督、升级或恢复的内部事实与能力。

随后用户要求对话成为核心、团队状态放右侧，并将“概览”改名“工作台”；模板创建必须能持续对话，随沟通更新可预览草稿后保存。布局调整不改变既有归属与治理规则，模板生成也不能只停留在一次输入后展示固定草稿。

本轮用户纠正知识挂载对象为员工，共享源更新对所有挂载该知识的员工可见，未挂载同事不继承。最终又明确知识对 Agent 不可改，可自迭代的是数字员工模板；此前团队挂载及两类可迭代知识解释不作为有效规则。知识源的当前版本、员工工作版本和模型实际采用内容分别记录，避免把源更新误称为所有运行已经切换。

### 1.2 已确认的来源与功能目标

| 来源 | 用户明确的内容 | 需求含义 |
| --- | --- | --- |
| D18 | 平台通过 Prompt 生成与配置数字员工；Prompt 定义流程，大模型控制团队运行，员工相互监督 | 提供员工、团队、流程与真实执行的管理能力 |
| D19 | 员工拿不准方案向上级提交，上级仍无法解决继续向上，最终反馈用户 | 支持可追溯的逐级评估与用户决定 |
| D20 | 新增员工或修改员工、团队流程的 Prompt，由用户决定，员工只能建议；后续 D34 局部开放模板迭代 | 用户仍掌握实际员工/团队流程变更权；模板自迭代不等于同步员工或组织扩权 |
| D21 | 支持已有项目改造和新项目开发 | 研发应用应能表达现有基线和空白起点，不能仅能演示从零生成 |
| D22 | 保留模型灵活度，不限制员工能力，不局限场景 | 岗位、场景、流程步骤、产物类型均开放；模型可自主选择方法、计划和协作方式 |
| D23 | 通用团队平台后续有业务团队，只需先搭基础设施 | 当前建设通用执行与管理底座；研发和业务团队通过配置承载，不内置为两套行业应用 |
| D24 | 概览呈现各团队群聊、进展和空闲程度，通过 @我 提示处理事项；不需要独立运行记录和我的待办 | 工作与处理入口回到对应群聊，内部运行和证据按需展开，已读不代表同意 |
| D25 | 数字员工入口管理模板的能力 Skills，模板可用于创建员工 | 模板、Skills 与实际员工分开管理；模板可多次使用，但不自动改写既有员工 |
| D26 | 团队展示本团队实际员工，同一个实际员工只能在一个团队 | 每个实际员工唯一 teamId；从同模板在不同团队创建员工时产生不同身份和上下文 |
| D27 | 模板必须支持对话生成，继续沟通修改草稿，再明确保存 | 保留多轮来源、当前草稿与保存结果，不固定问答轮数，不把未保存草稿当作已生效模板 |
| D28 | 概览改名工作台，以对话为核心、团队状态放右侧 | 主体群聊与右侧团队状态协调呈现，具体宽度和手机展开形式属交互设计，不另定业务规则 |
| D29 | 每个团队有项目库，归档项目文档 | 团队内可有多个项目，文档保留版本与来源，项目库嵌在团队下，不新增主导航 |
| D30 | 提供版本管理工具，支持团队内多需求并行开发 | 需求、文档/代码基线、工作分支/隔离空间和集成结果可关联；Git 服务商、仓库映射与合并/冲突政策未定 |
| D31 | 团队首页不直接列员工，点击进入详情管理；简介可展示负责项目、人数、产品/模块描述等 | 首页摘要可呈现实际归属项目和人数，开放描述不固化为研发字段；实际员工及项目库在所属团队详情管理，默认标签和视觉样式仍为交互选择 |
| D32 | 信息挂载在员工身上，不是团队 | 只建立 employeeId 与知识源的挂载；团队视图不产生授权、全队共享或新成员继承 |
| D33 | 更新共享源，所有挂载对象可见；按员工挂载纠正适用 | 人维护源的新版本后，所有显式挂载员工可见更新；不向未挂载同事扩散，运行实际采用版本另记 |
| D34 | 知识对 Agent 不可改，数字员工模板可自迭代 | 人可维护知识并追加版本；员工可迭代模板 Prompt/Skills，保存来源/历史，不因此改写实际员工、团队流程、分类或挂载 |
| D35 | 团队需展示层级和上下级管理，采用组织树/拖拽交互方向 | 用户在团队详情调整关系、检查后明确保存，提供等效非拖拽入口；本版单直属上级是原型形式，职级/岗位开放，监督关系独立 |
| D36 | 用户认可工作台优化，本轮落实决策上下文、交付证据及右侧摘要 | @我 可看问题/尝试/各级意见/候选代价/影响/所需决定；交付按版本看检查和未验证；右侧显示目标/进展/阻塞/下一步/更新时间，未知过期不冒充空闲；不据此定稿其他开放政策 |

需要实现的基础闭环：用户生成和管理模板及 Skills → 在团队中创建实际员工并配置关系与流程 → 在团队群聊表达目标 → 模型组织工作与沟通 → 实际执行、交付和监督 → 拿不准逐级升级并在群聊 @我 → 用户在上下文中处理并查看结果。

### 1.3 本期范围与非目标

本期基础设施包含：多轮对话生成模板及 Skills/版本与自迭代、唯一团队归属的实际员工、上下级配置、团队群聊与 @我、开放目标与上下文、Prompt 流程、模型调度、工具执行、交付监督、升级与用户决定、内部运行控制和恢复，以及员工知识挂载/只读使用和共享源维护。主要入口为工作台、数字员工模板、团队、知识库；团队首页展示摘要，员工与项目等进入所属团队详情后管理。工作台以对话为核心，团队状态置于右侧，运行、任务、证据可按需展开，不要求独立顶级页面。

团队内的多项目库、项目文档归档与版本、并行需求及版本协作继续保留。项目库从团队及工作消息进入，不另设项目主导航；本轮知识库新增主入口，替代 v0.4 仅三入口的范围描述，不将工作台改成资源管理首页。业务团队可仅使用文档/资料能力，无代码仓库的工作仍可运行。知识只挂载到实际员工，团队详情的“员工知识”仅是本队逐员工视图。

范围边界：

- 提供可配置的通用平台，不把完整研发管理系统、CRM、销售或其他业务应用作为本次必须内置的产品。
- 岗位模板、团队示例和行业示例用于上手与验收，不构成员工能力上限；用户定义新岗位或新工作无需修改平台业务代码或登记场景枚举。
- 本期不确定新框架、重写技术栈、生产发布或外部业务系统的具体接入清单。现有技术栈与可用执行环境先作为评估基础。
- 本文交付需求分析，不以生成员工介绍、聊天记录或流程图冒充基础设施已经运行。
- 保留用户已有产品与资料；具体旧页面、CLI、协作功能如何迁移，在开放事项中单独决定，不随新定位直接删除。
- D24 已授权取消独立运行记录、我的待办入口，不需要再次请求该项界面收敛授权；数据、历史和内部执行能力继续保留。

### 1.4 术语与灵活度边界

| 术语 | 含义与要求 |
| --- | --- |
| 数字员工模板 | 可复用的工作 Prompt、职责、Skills 和能力素材；在数字员工入口管理，不是已经加入多个团队的实际员工 |
| 模板生成对话与草稿 | 用户持续表达和修订要求，平台按多轮上下文更新可预览配置；对话、当前草稿与明确保存后的模板分别识别 |
| 模板 Skill | 用户管理的能力说明、工作指令或可引用素材及其版本；不是岗位工具白名单，不自动授予外部账号权限 |
| 团队实际员工 | 由模板等用户决定的配置创建的独立身份，具有唯一 teamId、自己的工作版本与上下文；不能用同一实际员工挂接多个团队 |
| 员工运行实例 | 本团队某个实际员工在某次工作中的执行上下文；实例不是新员工身份，也不改变该员工的团队归属 |
| 团队群聊 | 团队工作和用户管理的主要入口，承载目标、沟通、进展、产物、监督与处理卡片；不等于仅保存聊天文本即可替代内部事实 |
| @我事项 | 团队消息中需要管理者关注或决定的引用；未读、已读、处理中、已作决定和已应用分别识别，读过消息不构成许可 |
| 组织关系 | 上下级用于处理拿不准的问题；监督关系用于检查工作，两者可分别表达，不能由岗位名称推断 |
| 流程 Prompt | 用户决定的协作要求与原则；可以描述顺序、检查或其他约定，平台不要求转换成固定业务阶段图 |
| 运行计划 | 模型依据现场情况形成、调整的任务、分工和方法；在有效指令内重规划，不等于修改流程 Prompt |
| 交付物 | 任意工作成果，可为文字、表格、代码、图像、资料、报告或外部结果的引用，不限定软件文件 |
| 验证事实 | 实际观察或执行的结果；与员工判断、管理者接受决定分开记录 |
| 团队项目库 | 一个团队下多个项目的集合；每项目组织文档、需求、版本工作及相关事实，不是跨团队共享实际员工或上下文的入口 |
| 项目文档版本 | 归档的确定内容、来源与修订，关联适用项目/需求；归档不自动代表文档已获批准，也不覆盖旧版评审 |
| 并行需求工作上下文 | 同项目中某需求使用的资料/文档/代码基线、分支、任务与执行空间；不同需求的写入和上下文可区分并隔离 |
| 版本协作与集成 | 记录需求所用工作分支/版本、目标基线、检查和集成结果；实际服务与授权政策待定，准备集成不等于已合并 |
| 共享知识源与版本 | 人维护、Agent 只读的知识内容；新版本成为共享源当前内容，对所有显式挂载员工可见，历史内容和来源保留 |
| 员工知识挂载 | 用户将知识源挂到某实际 employeeId 的关系；不以 teamId 授权，不向同队或同模板员工继承 |
| 模板自迭代 | 员工修订模板 Prompt/Skills 并记录新模板版本、原因和来源；不等于创建员工、同步实际员工工作配置或改写团队流程 |

员工可以在可用环境中选择工具、编写辅助脚本、组合方法、查找资料、请求协助和调整任务计划，不因岗位或团队类型预先拒绝这些方法。实际资源是否可达如实反馈；按 D34 自迭代模板与直接改写实际员工/团队流程分开，后者仍遵守 D20。知识挂载提供资料读取范围，不自动赋予知识写权或更高规则权限。

模板更新、Skills 调整与既有实际员工的同步策略尚未决定（Q-07）。从同一模板创建的员工分别有自己的身份和上下文；保存新模板版本不意味着批量热改这些员工，也不自动改变在途运行。

## 2. 用户与场景

### 2.1 角色

| 角色 | 责任与边界 |
| --- | --- |
| 管理者（人类用户） | 提出目标，决定员工与规则调整，查看运行、主动介入、处理逐级升级到自己的事项 |
| 数字员工 | 按有效指令工作、沟通、交付、检查与提出建议；拿不准时向其上级提交评估 |
| 上级员工 | 评估下级的问题；能解决则提供意见，仍无法解决继续升级。上级身份不自动取得改写组织规则或用户目标的权限 |
| 监督员工 | 依据约定检查具体工作与产物，提出问题并参与复核；不因发出监督意见自动成为对方上级 |
| 平台 | 提供模型上下文、协作执行、事实记录和控制入口，不预设某个岗位必须具备或不得具备什么业务能力 |

### 2.2 用户故事

| 编号 | 用户故事 | 可观察结果 |
| --- | --- | --- |
| SC-01 | 作为管理者，我希望持续对话生成员工模板、预览并修订工作 Prompt/Skills，明确保存后再用于团队 | 生成对话、草稿与已保存模板可辨；来源不丢失，实际员工仍分别创建 |
| SC-02 | 作为管理者，我希望先浏览团队摘要，进入详情后用组织树查看并调整上下级、管理员工和协作规则 | 首页不铺员工明细；树/关系草稿和保存结果可辨，变化仅属于本团队；岗位和职级开放，手机可完成调整 |
| SC-03 | 作为管理者，我希望员工自主分工、沟通和选择方法，以便减少逐项派单 | 模型的任务安排与实际工作可追溯，必要时能重规划和交接 |
| SC-04 | 作为员工，我希望检查彼此产物并纠正问题，以便使监督影响实际交付 | 问题、修正与复核对应明确产物与版本，不仅是一条评论 |
| SC-05 | 作为拿不准方案的员工，我希望上级逐级评估，以便团队内部先处理无法确定的问题 | 上级能解决、需继续升级、最终需用户决定的路径均可运行 |
| SC-06 | 作为管理者，我希望在群聊查看工作依据、提出变更并控制工作，以便管理长期任务 | 运行和证据可展开，控制不要求进入独立页面；组织变更不静默混用规则 |
| SC-07 | 作为管理者，我希望同一基础设施既能承载研发团队，也能承载业务团队，以便持续扩展用途 | 不改平台业务代码即可配置两类任务；无代码仓库的工作同样可以运行和交付 |
| SC-08 | 作为管理者，我希望以群聊为核心，在 @我 上下文中决定事项、查看交付证据，并从右侧了解团队目标/进展/阻塞/下一步及更新时间 | 减少往返查背景，能区分实际检查和未验证、未知和过期；阅读不自动同意，回复不冒充已经执行或恢复 |
| SC-09 | 作为管理者，我希望在团队项目库管理多个项目、归档文档并查看修订 | 能定位文档内容、版本、来源和关联需求，历史不被新版本覆盖，数据不串到其他团队 |
| SC-10 | 作为管理者，我希望团队在同项目并行推进多个需求，并用版本工具跟踪隔离工作与集成 | 不同需求采用的基线、分支、上下文和结果分别可查，冲突或未知结果不会显示已集成 |
| SC-11 | 作为管理者，我希望将同一知识源挂到指定员工，人维护源后所有挂载员工可见更新 | 未挂载同队员工看不到；团队视图仅按员工汇总；来源版本和实际采用版本可辨 |
| SC-12 | 作为管理者，我希望知识被 Agent 只读使用，员工通过迭代模板完善工作方式 | 知识不被 Agent 改写；新模板版本有修改来源与历史，不自动覆盖实际员工/团队流程 |

## 3. 功能需求

DET 编号保持稳定；D24～D26 将员工管理细化为模板/Skills 与团队实际员工，并收敛主要界面。旧探索中跨团队复用同一实际员工的表述不再有效。下列行为不代表技术方案已批准，细化建议与未决政策见 §8。

### 3.1 DET-01 员工模板生成、Skills 管理和复用

- **输入**：用户自然语言初始要求、连续补充/修订的对话、可选资料和已有模板；岗位名称、专业领域和 Skills 开放。
- **处理**：用户与平台持续沟通，模型结合多轮上下文生成和修改模板草稿，预览工作 Prompt、责任、协作及 Skills；支持继续修订再由用户明确保存，不强制固定问答轮数。既有模板及 Skills 仍可通过编辑方式维护。
- **输出**：可预览草稿、逐轮用户要求与生成反馈、修订来源，以及明确保存后的模板/Skills 版本。草稿生成和继续沟通不自动保存、生效或创建实际员工；保存版本关联其生成对话和采用草稿。
- **分支**：失败保留输入、对话及上一有效草稿；歧义指出具体问题，可继续对话修改；资料或工具不可用时如实说明，不把能力描述冒充真实执行成功。离开或取消不得伪报草稿已经保存。
- 模板及 Skills 在数字员工入口管理；用户创建时的多轮草稿仍明确保存。D34 允许员工对模板 Prompt/Skills 自迭代，保存有执行者、原因、依据及前后内容的新模板版本，不为每次模板迭代新增用户审批。模型选择工具和辅助脚本也不一律视为模板变更。
- 保存新模板或 Skill 版本不自动更新既有实际员工；是否同步、如何选择员工及如何作用于在途工作，保留 Q-07/Q-04。
- **模板自迭代**：员工可基于工作反馈或经验修订目标模板的 Prompt/Skills，记录目标模板、原基线、修改理由、员工/运行来源及新版本；不强制再次由用户批准模板迭代。失败或并发冲突保留旧版及候选内容，不伪报新版本已保存，冲突处理见 Q-11。迭代不创建实际员工，不直接修改知识或团队流程，不代表既有员工已采用新模板。

### 3.2 DET-02 团队实际员工、层级和协作关系

- **输入**：用户的团队要求、所选模板版本或明确生成要求、实际员工配置、责任和关系描述。
- **处理**：用户在团队中创建实际员工；每次创建新 employeeId，绑定唯一 teamId。人数、岗位和职级开放，平台可生成组织草案，由用户决定，名称不自动产生权限。团队详情以组织树呈现上下级，本版采用单直属上级形式；用户可拖拽或选择上级进行等效调整，预览关系草稿并明确保存。
- **输出**：团队首页仅展示可进入的团队摘要，可含实际负责项目、人数、产品/模块等开放描述；进入详情后展示和管理本团队的实际员工、工作版本、模板来源及关系，可定位上级与监督职责。首页不直接铺开员工列表或逐员工管理控件；模板上下文中为团队创建员工的入口不因此取消。
- **归属约束**：同一实际员工不能挂接多个团队。同模板用于另一团队时创建新的员工身份和上下文，不能将现有员工 ID 直接复用为另一团队成员；运行实例也不能改变归属。
- **分支**：跨团队挂接员工、选择自身或其下属作为上级产生的环、无效上级均应识别，保留上一有效关系和可修正草稿；不因拖拽失败静默改团队归属。具体异常升级路径及是否支持多上级见 Q-03，不重新悬置树形管理方向。
- 正常升级路径最终能反馈用户；顶层员工与最终人类管理者可辨，不把用户创建成数字员工。保存关系后可追溯原/新上级及关系版本；不据此宣称在途运行已切换，生效见 Q-04。监督关系单独管理，可以相互进行，不套用上下级树的无环或单父节点约束。

### 3.3 DET-03 通过 Prompt 定义协作流程

- **输入**：开放自然语言的流程要求、目标、约定和可选参考资料。
- **处理**：保留原始 Prompt 与有效工作指令，展示必要的解释和待澄清内容；不要求用户编写流程代码，不固定岗位清单、阶段、轮流发言顺序或业务场景。
- **输出**：有版本的流程定义，可用于不同团队和不同工作目标。
- **分支**：规则冲突或含糊时明确指出，保留用户输入并支持修订；解释摘要不能无记录地替换用户规则。
- 用户可以规定严格顺序，也可以仅描述目标、责任和检查原则。平台应保留模型在这些规则内选择路线、补充步骤、并行安排和重规划的空间。

### 3.4 DET-04 模型驱动的运行与动态任务安排

- **输入**：工作目标、团队和流程版本、已有产物、上下文、通信、执行反馈及用户指令。
- **处理**：模型决定后续任务、执行员工、沟通对象、方法、工具、交接、评估与返工。平台执行对应动作并反馈真实结果，支持多轮持续推进。
- **输出**：任务、责任员工、依赖、决策依据摘要、实际动作及结果，能在界面中直接查看。
- 每次运行应能明确最终接收升级事项的人类管理者，不能仅靠空间成员列表或员工自由选择猜测；模型调用和员工消息不改变该绑定。
- **分支**：员工或工具不存在、上下文不足、动作失败或结果未知时，返回可供模型继续判断的实际状态；拿不准的方案进入 DET-09。
- 模型可以动态新增子任务和为既有员工建立执行实例；不能借此创建未经用户决定的新员工身份或改写员工与流程 Prompt。
- 执行实例引用本团队的实际员工及确定工作版本；模板复用或实例创建不能让同一实际员工同时归属其他团队。
- 需要实际执行的任务不能仅凭模型文本宣布执行成功；纯分析任务可用持久化分析产物验收，不机械要求每种任务必须调用外部工具。

### 3.5 DET-10 员工沟通、交接和上下文

- **输入**：团队群聊中员工或用户发送的消息、@对象、关联任务、问题和资料引用；普通讨论不强制先创建独立运行。
- **处理**：支持员工、上下级与管理者在团队群聊沟通、交接、请求协助和补充上下文；可从消息展开相关任务、产物、检查与决定，区分用户、实际员工实例和系统来源。
- **输出**：有团队、发送者、接收者、关联对象和时间的通信记录，以及进展摘要、@我提示和可追溯处理结果。
- **分支**：无法投递、重复投递、接收者不可用或消息尚未处理时状态可见；不以“发送了消息”替代“完成了交接”或“对方已决定”。
- 员工不能通过伪造用户来源的消息取得变更规则的权限；普通员工消息仍可提供事实、建议和协作输入。
- 消息已发送、已读、事项处理中、已作决定和变更已应用分别记录。打开群聊、读过 @我 或将消息标为已读，不构成批准、问题解决或实际执行；具体决定关联对应升级或变更事实。

### 3.6 DET-11 开放工具与实际执行

- **输入**：模型选择的动作、参数、关联任务及可用环境。
- **处理**：提供通用执行入口与可扩展的工具/Skill/MCP 接入，支持查询、文件、脚本、浏览器及后续能力；工具可发现、组合和扩展，岗位不是工具执行白名单。
- **输出**：实际执行的身份、输入、开始和结束情况、结果、错误及证据引用；可区分未执行、进行中、成功、失败、取消和结果未知。
- **分支**：外部系统、凭据或资源不可用时保留失败及下一步，不伪造业务结果；存在副作用但结果未知的动作先核实，再判断如何继续，避免直接重复执行。
- 具体工具连接依赖实际环境和用户提供的访问条件。平台接口和执行协议应允许新增工具，无需为每个行业改写调度主流程。

### 3.7 DET-05 产物监督、问题修正与复核

- **输入**：任意类型的交付物版本、检查要求、可获得的证据和员工意见。
- **处理**：支持检查、提出问题、安排修正及针对新结果复核。模型依据有效流程安排检查时点与对象；不固定所有工作都必须经过同一套审批。
- **输出**：检查对象、版本、依据、结论、问题、责任和处理记录；“提出问题”“已修正”“复核通过”和“接受结果”分别识别。
- **分支**：员工相互认可而实际验证失败时保留失败；证据不足时明确未验证或无法判断；更换产物版本后进行影响判断，旧评审不自动覆盖新版本。
- 监督的阻断、解除和改派权限需要由有效规则明确，尚未决定的全局默认政策保留 Q-01；上级评估和用户接受均不能把失败事实改写成成功。

### 3.8 DET-09 拿不准方案时逐级升级

- **决策上下文（D36）**：在群聊 @我 中展示具体问题、已有尝试、逐级意见、候选方案与已知代价、影响范围及需要用户决定的内容；相关版本/事实可展开。没有尝试、无法比较代价或暂无候选时如实说明，不为填卡片编造结论，不将模型推荐当成用户决定。

- **输入**：员工提出的具体问题、不确定原因、相关资料、产物、已有尝试和候选方案。
- **处理**：按上下级关系提交评估；上级能解决则记录意见，上级仍无法解决继续向上，最终反馈用户。支持上级补充核查或请求资料。
- **输出**：当前处理者、已经过的层级、各级评估、剩余问题及最终决定来源；最终仍无法解决时，在对应团队群聊 @该次工作的管理者，展开后可查看必要背景并处理，不要求独立我的待办页面。
- **分支**：无人答复、反复转交、回答仍含糊或层级配置异常不能被视为问题已经解决；等待与恢复细节见 Q-02/Q-03。
- 接到处理意见后，应能关联决定、适用范围与后续任务，保留复核机会。该能力不产生阶段全审批，也不扩大上级的组织修改权。

### 3.9 DET-06 运行观察、干预、暂停与恢复

- **右侧摘要（D36）**：展示当前团队目标、当前工作/进展、阻塞、下一步及来源更新时间，保持群聊为主；移动端按需展开。摘要关联工作事实，未知、过期、无当前目标和真实空闲分别可辨，不用“无数据”推导空闲，也不以重绘界面刷新事实时间。统计/过期口径仍按 Q-05 定稿，下一步描述不代表已经执行。

- **输入**：用户的查看、补充指令、暂停、恢复或终止请求，以及服务中断后的状态。
- **处理**：在团队群聊展示工作进展与空闲程度，按需展开目标、员工活动、任务依赖、产物、监督、升级和资源事实；处理控制请求并返回实际状态，不要求独立运行记录页面。
- **输出**：可恢复的运行记录，以及已完成、未执行、在途和结果未知的事项；控制请求已接收与控制动作已生效分别可辨。
- **分支**：在途工具无法立即取消、服务重启、连接重建和消息重复时保留状态与已有成果；恢复先核实未知结果，不盲目重做。
- 不在需求中默认等待期间全团队停止或其他工作继续。平台需支持表达等待范围与依赖，具体政策在 Q-02 明确。
- 团队忙碌、空闲、等待或状态未知应有对应活动依据；不以未读消息数量推断负载，不将未知或过期状态显示为空闲。具体统计口径与时效由 Q-05 细化，不预设统一百分比。

### 3.10 DET-07 通用交付与结果判断

- **交付证据（D36）**：在群聊按需查看具体产物/结果及版本、实际检查方法与结果、未验证范围和剩余问题，定位原始执行/检查事实。没有实际检查时明确未执行或未验证；不将员工描述当作已执行证据，不把旧版通过结论用于新版，不将静态演示标成真实验证。交付类型开放，不机械要求业务分析成果具备代码提交或构建记录。

- **输入**：目标、完成要求、实际产物、验证、监督结论、缺陷及待决定事项。
- **处理**：模型整理交付结果；平台将总结与实际产物、执行和检查记录关联。
- **输出**：可以取得的成果、覆盖情况、依据、未验证内容、未解决问题和后续建议。
- **分支**：缺少所要求产物，或动作尚未完成、失败、未验证，不能将相应内容显示为已验证成功。整体交付是否满足目标，依据该次工作的有效要求和规则判断；遗留问题持续披露，不默认任意未关闭问题都阻断全部交付。
- 执行结束、验证通过、用户接受、外部发布为不同事实。不同团队可有不同完成要求，不以“代码构建通过”作为所有团队统一的交付条件。

### 3.11 DET-08 版本、变更影响与历史追溯

- **输入**：模板及 Skills、实际员工、组织、流程、目标、产物和评审的版本以及运行中变更。
- **处理**：识别每次工作实际采用的版本；变更展示前后内容和影响，记录生效依据与适用范围，保留历史引用。
- **输出**：可定位的有效指令、当前版本、历史决定和受影响任务；历史结论不会随“当前版本”指针变化而被改写。
- **分支**：用户请求基于过期版本变更时指出冲突；运行中修改是否立即生效或仅对后续运行生效，见 Q-04，不静默混用规则。
- 模板来源版本、实际员工工作版本和运行采用版本分别保留；模板修改不得无记录地改变既有员工，具体同步规则见 Q-07。

### 3.12 DET-12 分范围的配置变更权

- **输入**：用户明确的创建员工、调整实际员工/团队流程、知识分类/挂载指令，或员工建议；模板自迭代另标来源。
- **处理**：员工建议包含候选内容和理由，与需要用户决定的生效配置分开。新增员工、直接调整实际员工/团队流程以及知识分类/挂载由用户明确决定；D34 的模板 Prompt/Skills 自迭代可记录新模板版本，不冒充用户决定，也不自动应用到既有员工。
- **输出**：建议、用户决定、变更内容、来源、版本及生效记录。
- **分支**：建议被拒绝或未回复时不生效；员工通过工具、消息、知识记录或其他途径绕过用户决定修改有效规则，应被识别并保留记录。
- 用户通过 Prompt 或界面发起明确操作可作为该项决定依据，不增设重复确认。运行实例、任务分派、方法与辅助脚本不一律当作组织变更；模板自迭代按 D34 记录，直接写入实际员工/团队流程时适用用户决定规则。
- 员工建议和用户处理卡片可在团队群聊 @我 展示；读过卡片不代表采纳。模板保存、为团队创建新员工和同步既有员工是不同作用范围，不能由一次未说明范围的模板保存默认为批量同步。

### 3.13 DET-13 通用工作目标与基础管理界面

- **输入**：用户开放的目标、资料、约束和期望成果；可选现有工作基线。
- **处理**：核心入口为工作台、数字员工模板、团队、知识库。工作台对话占主要区域，右侧呈现团队状态及必要切换，避免两侧重复摘要挤占群聊；数字员工管理模板和 Skills。团队首页仅保留可进入的摘要，进入详情后管理员工、项目库和逐员工知识挂载。知识库统一管理共享源，不以入口可见代替员工授权。任务、证据和处理记录按需展开，不设独立运行记录/我的待办顶级界面。
- **输出**：可切换的团队群聊、活动与空闲摘要、待处理 @我、可管理的目标及资料、可展开的运行和交付依据。代码、软件版本和业务记录均为可选上下文，不是所有工作的必填前提。
- **分支**：输入缺失时指出具体需要什么；既有资料与模型生成内容的来源可辨。研发示例支持现有代码变更和空白起点，业务示例可以无代码仓库运行。
- 无消息、无团队、空闲、状态未知和没有 @我 事项应可辨；新团队不继承其他团队的消息、实际员工、产物或决定。界面简化不代表仅存聊天文本，更不授权删除内部运行或历史事实。
- “工作台”是当前用户可见名称。桌面栏宽、状态详情展开和手机团队抽屉属于本轮交互选择；移动端仍以完整群聊为主且团队切换、状态、@我 可达，不据此固定全部设备布局。
- 团队项目库嵌在团队入口下，工作消息可关联项目、文档或需求并按需打开；不新增项目主导航，也不要求每条普通群聊都先选择软件项目。
- 团队简介支持用户表达所负责产品、模块或其他工作范围；首页可显示负责项目与人数，项目名称和人数来自本团队归属事实，未建项目时不虚构清单。描述采用开放内容，不强制所有团队填写软件产品或模块字段。

### 3.14 DET-14 团队项目库与文档归档

- **输入**：团队、项目名称/目标与资料，文档内容或引用、来源、修订说明及可选关联需求。
- **处理**：一个团队管理多个项目，在项目中归档文档并新增内容版本；用户或员工按有效工作规则整理资料，保留作者/来源、修订及适用范围，不把归档自动当作业务批准。
- **输出**：团队内项目列表、项目文档及版本历史、当前采用版本，以及与需求、产物、检查或工作消息的关联。
- **分支**：内容无法取得、上传失败或基于过期版本修改时如实反馈，不伪报归档成功；文档更新不覆盖旧内容或旧版评审。项目、文档及需求引用校验团队归属，不能跨团队串用。
- 项目库用于组织资料，不自动将项目文档改写为员工长期 Prompt；涉及长期指令的变化仍遵守 D20。

### 3.15 DET-15 多需求并行与版本协作

- **输入**：团队项目、并行需求目标、采用文档/代码基线、工作分支或等效隔离空间、可用版本工具和检查要求。
- **处理**：模型可按有效流程为多个需求分工、建立独立工作上下文并持续推进；分别关联需求 ID、所用版本、任务、分支及执行空间，避免并行修改共用未区分的上下文或写入区域。员工可有不同任务实例，但实际员工的唯一团队归属不变。
- **输出**：各需求的进展、采用基线、文档/代码版本、工作分支、检查与集成尝试；能追溯集成来源、目标版本、实际结果及冲突。
- **分支**：需求或项目不属于本团队、分支/工作区无法定位、基线变化、版本工具不可用、集成冲突或结果未知时保留事实与影响，不能只凭模型声明显示已切换分支或集成成功。未知外部结果先核实，不能直接重复有副作用的操作。
- 旧检查结论不自动覆盖变更后的文档或代码。哪些工作受冲突影响按依赖和有效流程判断，不擅自默认全团队停工；拿不准的处理方案按 DET-09 逐级升级。
- 提供版本管理能力，但不固定 Git 服务商、分支命名、一项目一仓库、每需求永久单分支或每次合并都人工审批。接入及仓库映射见 Q-08，合并授权与冲突处理见 Q-09；在有效规则未明确前不将某员工身份自动等同于有合并权。

### 3.16 DET-16 员工知识挂载与共享源

- **输入**：人维护的知识名称、内容/资料引用、分类、修订说明，以及明确的实际 employeeId 挂载对象；读取时包含当前实际员工身份。
- **处理**：人创建和维护知识源，追加内容版本并保留历史；人按实际员工逐一挂载或卸载。知识库集中管理知识源，团队详情的“员工知识”仅是本队逐员工视图，不创建 teamId 挂载，也不因同队、同模板或新加入员工而继承。Agent 只读使用知识，不写入、删除或修改其分类/挂载。
- **输出**：知识源当前版本、历史内容和来源、逐员工挂载及实际读取事实。人更新共享源后，所有显式挂载该知识的员工可见更新；不同团队员工可分别显式挂载同一源，不据此共享其他项目或上下文。
- **版本采用**：源更新可见不等于当前模型上下文已经替换。每次实际读取/使用应能定位知识源及版本、员工/运行来源；读取时点、在途采用和卸载后既有上下文如何处理见 Q-10，不默认批量热改正在运行的上下文。
- **分支**：内容不可取得、来源失效、挂载对象不存在或未授权时如实提示，不伪报已读取；未挂载员工不能仅凭同队身份直接读取知识源。人维护基于过期版本时不静默覆盖，冲突与恢复见 Q-11。模板自迭代不得写回知识或自行改变挂载；员工已读知识形成的群聊/产物及转交内容如何控制另见 Q-12。

## 4. 数据模型

本节给出需要保存的业务事实；详细字段、类型、约束与关系见[候选附录](infrastructure_contract_candidates.md)。这些是系统设计输入，不是已经批准的 DDL。

| 实体组 | 必须表达的事实 | 关键约束 |
| --- | --- | --- |
| 模板与 Skills 版本 | 可复用模板、工作 Prompt、能力素材、修订与来源 | 模板不是实际员工；Skills 不是工具白名单，更新不默认批量同步既有员工 |
| 模板自迭代记录 | 目标模板、原/新版本、理由、员工/运行和修改来源 | 员工可记录模板新版本，不伪装用户决定，不自动改实际员工或团队流程 |
| 共享知识源与内容版本 | 人维护的名称、分类、当前版本、内容引用和历史来源 | Agent 只读；人追加版本更新共享源，挂载员工可见，不覆盖历史内容 |
| 员工知识挂载与读取 | 实际 employeeId、知识源、用户挂载/卸载记录、实际读取/采用版本 | 不含 teamId 挂载授权；共享源更新不等于在途模型已采用，未挂载不继承 |
| 模板生成对话与草稿 | 原始要求、后续修订、生成反馈、当前草稿及明确保存引用 | 多轮来源完整；保存明确采用哪份草稿，未保存不算有效模板 |
| 团队实际员工与工作版本 | 新员工身份、唯一 teamId、模板来源、采用的 Prompt/Skills 和上下文 | 同一实际员工只能在一个团队；同模板在不同团队创建不同 employeeId，运行实例不改变归属 |
| 团队及关系 | 本团队员工组成、责任、上下级、监督及对应版本 | 管理和监督关系分开；正常升级最终反馈用户，配置异常可见 |
| 团队项目与文档版本 | 一个团队内的多个项目、文档内容/来源/修订与采用引用 | 项目与文档归属一致，保留历史内容和评审，不把归档当作批准 |
| 并行需求与版本协作 | 需求、输入基线、分支/工作上下文、检查、集成来源/目标与结果 | 不同需求上下文和写入可隔离；不跨团队串用，不将准备或未知状态当作已合并 |
| 通用目标与上下文 | 用户目标、资料、约束、期望成果及可选已有基线 | 不强制代码仓库或行业类型；来源和版本可追溯 |
| Prompt 流程与版本 | 原始指令、有效指令、解释和变更来源 | 指令变更与模型日常重规划分开；模型解释不静默替代原指令 |
| 运行、实例与任务 | 采用版本、员工上下文、责任、依赖、等待和实际状态 | 业务任务类型开放；技术生命周期不固化业务阶段 |
| 团队群聊、@我与交接 | 团队、发送者/接收者、@对象、工作关联和处理结果；决策问题、尝试、各级意见、候选代价、影响与所需决定 | 用户/员工/系统来源可辨；发送、已读、处理、决定、实际应用分别记录；未知信息如实标记 |
| 执行与证据 | 动作、输入、结果、外部状态、关联标识与原始输出 | 结果未知单独识别；实际验证与模型判断分开 |
| 产物、监督与问题 | 任意成果版本、实际检查方法/依据/结果、未验证范围、剩余问题、修正与复核 | 证据绑定明确对象/版本；员工判断、真实检查和接受决定分开，不因新展示卡片增加一套伪事实 |
| 升级与评估 | 问题、各级处理人、路径、意见及用户决定 | 无答复不是许可或解决；保留完整升级链 |
| 变更建议与决定 | 候选变更、发起人、用户决定、生效版本与范围 | 对新增员工、实际员工配置、团队流程及知识挂载，员工仅建议；D34 模板自迭代不要求伪造用户决定 |
| 运行事件与用量 | 排序、关联、状态变化、模型调用和资源记录 | 支持查询与恢复，不以易丢失的聊天或实时通知作为唯一事实源 |

存储评估先沿用现有 PostgreSQL、Redis 与 MinIO：持久业务事实与版本、通知和任务分发、产物与原始证据内容分别评估。具体表、索引、Redis key、事务与一致性机制交系统设计师确定，禁止用新需求直接宣称现有实现已满足可靠恢复。

| 共享知识源与员工挂载 | 人维护内容/版本及 employeeId 挂载，员工读取请求 | 共享源与历史、逐员工挂载、实际读取版本；Agent 只读，不以团队授权 | DET-16；D32～D34 |

| 团队群聊、@我、任务与事件 | 团队、发送者、@对象、工作关联、游标和显式处理 | 目标/进展/阻塞/下一步及事实时间、决策上下文、消息/mentions 与状态、可恢复位置；摘要不代替事实 | DET-04/06/09/10/13 |
| 执行、产物与监督 | 实际动作、产物版本、检查与证据 | 执行事实、确定内容引用、实际检查、未验证范围、剩余问题及复核；展示不冒充新验证 | DET-05/07/11 |
| 升级与决定 | 问题、当前员工、评估、意见或用户答复 | 当前处理者、路径、决定和相关待办 | DET-09 |
| 群聊变更建议与用户应用 | 候选内容、理由、旧版本、作用范围及用户决定 | 建议状态、决定、生效版本或未应用原因；读过 @我 不构成应用 | DET-08/12 |
| 团队项目库与文档版本 | 团队/项目、内容引用、修订说明、需求关联和基线 | 项目列表、文档版本、来源/历史与关联事实；不新设主导航 | DET-14 |

模型侧的调度与执行协议需要能够表达开放任务、消息、工具使用、监督和升级，并返回实际结果；其可扩展方式由系统设计师确定，不仅支持固定的研发动作。员工不得通过调用面向用户的管理操作伪造用户决定。

内部保留运行、动作、证据和决定资源，不因取消顶级页面而删除对应接口。面向团队的实际员工创建与查询必须校验唯一归属；不再采用全局选取同一实际员工并挂接多个团队的候选方案。

| N-07 恢复与未知结果 | 结果未知的外部动作先核实再决定继续或重试；已完成成果和历史失败不因恢复丢失 | 在动作发生后、回执前制造中断，检查补查、关联和副作用情况 |
| N-08 资源与性能 | 模板数量、实际员工、运行实例、模型并发和执行环境分别评估；团队进展/空闲摘要有时效和状态依据，不把现有沙箱容量当作员工人数上限 | 系统设计师给出并发、群聊事件负载、摘要口径、控制响应及资源指标，测试按该基线执行；见 Q-05 |

| N-11 并行版本隔离 | 同项目多个需求有可辨输入基线、工作分支/隔离空间、执行与结果，不能悄然共用会互相覆盖的写入上下文；集成结果与具体版本关联 | 并行修改两个需求并交叉检查文档/代码来源，验证隔离、版本变化及冲突/未知结果；具体工作区实现由系统设计师评估 |

### 7.2 错误与用户反馈语义

以下为错误分类和代码候选，供接口设计定稿；不是现有接口已提供这些响应。错误结构沿用 `{"error":{"code":"...","message":"..."}}`，并关联可查询的运行、任务或操作。

| 候选代码 | 触发条件 | 用户或模型可观察的处理 |
| --- | --- | --- |
| TEAM-4001 | 组织配置缺失、冲突或升级关系不可解析 | 指明对象、冲突和影响；保留草案/问题，提供修正入口，不能伪造上级 |
| RULE-4031 | 员工试图直接应用需用户决定的新增员工、实际员工配置、团队流程或知识挂载变更 | 保留建议能力，拒绝生效并说明需用户决定；不把正常重规划或 D34 模板自迭代误判为此错误 |
| KB-4031 | Agent 试图改写知识内容，或未挂载员工读取知识源 | 拒绝对应写入/读取且不伪报成功；人仍可维护源和挂载，团队成员身份不代替挂载 |
| REV-4091 | 写入基于过期版本或同幂等键内容冲突 | 返回冲突基线，允许获取最新版本后重新表达变更，不静默覆盖 |
| RUN-4091 | 控制或状态变更与当前事实不相符 | 返回当前状态和在途动作；重复操作按已确定语义返回，不伪报已停止 |
| EXEC-5021 | 模型服务、工具或外部依赖执行失败 | 记录实际失败和影响，反馈可供模型判断的结果；拿不准则逐级升级 |
| ESC-4091 | 评估或用户决定基于过期升级状态 | 展示当前处理者与有效评估，不重复应用旧决定 |

动作结果未知是独立执行状态，不等于客户端应自动重试的普通报错。查询动作本身成功时仍可返回未知状态、已经取得的证据和需要核实的事项。

## 9. 方案选型与设计输入

### 9.1 候选组织方式

| 方案 | 可取之处 | 主要代价与需验证之处 |
| --- | --- | --- |
| A：在现有共享会话上增加员工身份、指令与协作状态 | 可复用现有消息、界面和执行代码 | 需证明不会继续把团队等同单会话/单沙箱/单任务锁；版本、任务、通信、升级和恢复仍需完整事实模型 |
| B：明确通用团队运行对象，复用现有单次模型与工具执行能力 | 能分别表达团队配置、运行实例、动态计划、任务、监督和升级，并跨研发/业务使用 | 新增运行管理和迁移工作；现有执行器、总线、Prompt 传递与恢复不能直接视为满足要求 |

产品建议优先围绕 B 明确对象和行为，保留模型动态控制。最终模块边界、复用方式、并行与恢复实现由系统设计师评估；不在本分析中选择新的 Agent 框架、数据库或消息系统。

### 9.2 必须保持的设计方向

- 组织配置与运行计划分开：模型能灵活工作，用户仍决定员工和长期指令变化。
- 流程规则与真实状态分开：Prompt 表达规则，实际任务、产物、执行、监督和决定有可核查事实。
- 岗位和领域不进入封闭业务枚举：研发、销售、运营或混合团队均为配置实例。
- 扩展能力与运行内核分开：新增工具与工作类型不要求重写一套行业调度器。
- 共同生命周期与业务阶段分开：可以有运行/等待/结束等基础设施状态，不能据此强制所有团队遵循相同业务步骤。
- 模板复用与实际员工归属分开：模板可以多次采用，实际员工只有一个团队；实例或执行上下文不作为绕过归属的手段。
- 群聊入口与内部事实分开：运行、监督、决定和恢复仍有事实记录，用户从团队群聊按需查看，不再要求独立运行或待办页面。
- 团队项目与开放工作目标分开：团队可有多个项目及文档库，研发可关联需求和版本工具；没有软件项目或仓库的业务工作仍可进行。
- 并行上下文与集成事实分开：需求在独立工作基线/空间推进，最终集成按明确授权和实际检查结果记录，不以分支卡片或合并意图代替真实结果。
- 知识源与员工挂载分开：源更新共享，读取资格逐 employeeId 决定；团队视图不产生团队授权。
- 模板自迭代与现有员工生效分开：员工可改模板并保存来源/版本，不因此修改只读知识、批量替换员工工作指令或扩展到团队流程。

### 12.3 程序验证、模型质量与业务验收

模型质量需覆盖职责含糊、事实冲突、工具失败、能力依赖缺失、员工分歧和应升级但未识别的不确定问题。既要检查“已提出的不确定问题能否上报”，也要检查是否存在错误自信、隐藏失败或重复互评空转。测试方法、样例与通过口径需在规则和架构明确后形成，不能以模型自评或一次满意回答证明稳定质量。
