## 2. 产品侧需补清的规则

### R-01 模板自迭代需要真正改善后续工作

需求已允许员工迭代模板，但既有员工何时采用仍由 Q-07/Q-04 保留。当前可以产生很多模板版本，却无法据此判断下一次工作是否得到改善。这是价值链缺口，并非已有规则直接矛盾。

建议供用户决定：正在执行的任务固定原版本；新工作按明确的采用策略使用经过基本核验的新模板，记录版本并支持退回。需明确适用员工、采用时点和退回条件，不要求每次模板迭代逐次人工审批，也不把逐员工手工更新当作用户已决定的永久方案。

依据：需求 DET-01、DET-08、Q-04/Q-07；[模板迭代与采用约束](infrastructure_contract_candidates.md)。此项阻断实际模板迭代/采用能力的交接。

### R-02 组织树、监督和升级等待应形成完整闭环

用户已确定树形与拖拽方向。当前原型原先只在创建员工时选择上级，缺少完整总览与调整；本轮组织树用于补齐这个交互缺口。树表示汇报/上报关系，员工分工保持开放；监督关系独立，不要求它遵守上下级的树形约束。

仍需用户确认业务后果：监督者能否阻断；谁可解除或改派；一个问题升级后哪些任务等待；回复后具体恢复哪项工作。

建议提案：问题绑定具体任务和产物；依赖该决定的工作等待，其他工作按有效流程继续；上级不能裁决才逐级上报用户，收到决定后恢复明确的后续任务。此提案尚未获确认。验证还需覆盖员工错误自信未上报、互评通过但真实检查失败，不以统一信心分数代替判断。

依据：DET-02/05/09/06、Q-01～03。树形交互可完成；监督与等待后果未明确前，对应实际运行契约仍不能交接。

### R-03 知识挂载的含义需覆盖派生内容

已明确按员工挂载、共享源更新及知识 Agent 只读。尚未明确的是：挂载主要用于配置模型可直接检索的参考资料，还是还承担内容保密边界？

已挂载员工可能把知识写入群聊、交付物或自迭代模板，未挂载员工随后可能看到这些派生内容。仅校验原始知识读取接口无法决定这种传播是否允许，也不能在实施时擅自禁止正常协作。

建议明确两层含义：直接检索按挂载检查；协作产物与模板传播按用户确定的共享范围处理。若需要机密资料隔离，须进一步定义派生内容的允许范围。不可默认已经实现完整保密隔离。

依据：DET-10/16、N-12、共享模板与员工挂载候选。此项影响知识读取、群聊和模板迭代共同使用时的业务预期。

### R-04 自主运行要有成本、停止和交付依据

N-09 已要求资源可观察及无进展出口，但尚未给出预算耗尽或持续无进展后继续、等待或升级的最低业务预期；Q-09 也未决定真实集成动作可自主执行的范围。

建议提供可配置资源预算、持续无进展出口和有效终止入口；达到边界后保留成果与剩余问题并通知管理者。具体数值通过实际试运行确定，不把岗位能力、工作步骤或所有任务轮数固化。成功应依据可用产物、实际检查与剩余问题，不能依据讨论结束或忙碌状态。

依据：N-03/N-09、Q-09、DET-05/07。需由用户确认可接受后果；实现机制及具体测量由系统设计师负责。

这些差距阻断对应运行能力直接复用交付，不阻断继续调查、系统设计和隔离原型。容量、恢复效果及模型质量均未实测。

## 5. 建议的下一阶段

1. 由产品带着 R-01～R-04 的后果和提案确定必要业务规则；用户已决定的定位、员工归属、知识只读、模板可变及树形拖拽不重开。
2. 系统设计师完成团队运行、执行身份、版本采用、需求隔离、动作持久化和控制恢复契约；具体锁、幂等、Git 服务接入及沙箱映射在授权内自主评估，不将所有技术问题交用户选择。
3. 以一个真实目标贯穿可配团队、实际产物、交叉核查、一次升级和恢复；纳入知识与模板版本，再验证两需求并行及一个无代码仓库业务任务。它们是验收载体，不是岗位或场景限制。
4. 关键规则和技术设计成立后再拆开发任务。首个贯穿验证应进入实现顺序，而非所有界面/模块做完后才第一次验证。

优先观察人工介入次数与耗时、遗漏问题、重复执行、可用交付、模型/执行用量；不以聊天量、员工数量或一次满意输出证明质量。应包含错误自信、互评误判、相同文件并行修改、知识更新与工具执行后中断等重要场景。
