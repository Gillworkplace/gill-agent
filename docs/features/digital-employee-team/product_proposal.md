## 1. 用户目标与已明确的决定

来源为本次需求讨论，不能将本文建议视为用户已经决定。

| 编号 | 用户表达与本次明确的含义 | 确认状态 |
| --- | --- | --- |
| U-01 | “一个人管理一个团队”，覆盖产品需求分析、系统设计、开发、测试全流程 | 用户已明确 |
| U-02 | 员工指数字员工，通过 Prompt 配置；数字员工也由该平台生成 | 用户已明确；生成、修改和启用的具体交互待细化 |
| U-03 | “通过 prompt 去定义流程”“将运行交给大模型去控制” | 用户已明确；模型可自主调整哪些事项待决定 |
| U-04 | 通过员工之间相互监督，确保流程正确运行 | 用户已明确目标；监督权限、证据和争议处理机制待决定 |
| U-05 | 数字员工有上下级；拿不准方案时向上提交，由上级评估，上级仍无法解决则继续向上，最终反馈用户 | 用户已明确；权威决定见 D19；层级配置方式、等待和恢复细节待细化 |

产品价值在于：管理者表达目标、组织规则和交付要求，数字员工团队持续完成分工、交接、检查、修正与交付，管理者能够看清进展并介入重要取舍。

这里的产品、系统设计、开发、测试描述需要覆盖的职责。岗位名称、员工数量、协作方式与具体执行次序不据此固化。

U-05 明确的是遇到不确定问题时的处理路径，不据此增加每个阶段都需上级审批的规则；相互监督继续保留。上级评估也不能覆盖实际测试失败或未验证事实。

## 2. 核心概念与产品结构

下表是产品语义建议，不指定数据库、接口或技术框架。

| 对象 | 用户能表达或管理的内容 | 与其他对象的关系 |
| --- | --- | --- |
| 数字员工 | 通过 Prompt 描述需要什么员工；平台生成其工作 Prompt、职责、输入要求、交付标准、协作方式及所需能力，用户可以继续调整 | 员工定义可复用；某次工作中的执行记录、任务上下文与员工定义分开识别 |
| 数字员工团队 | 围绕一个目标选择或生成员工，描述责任分工、上下级关系、相互监督关系和协作约定 | 上下级决定不确定问题的升级路径，监督关系描述检查职责；具体配置方式待细化，岗位名称本身不决定上下级 |
| 项目与工作目标 | 要做的软件、现有代码和资料、用户目标、约束、交付要求 | 将需求、设计、代码、测试和问题记录关联到同一目标 |
| 流程 Prompt | 描述如何分工、何时交接、如何检查、什么情况返工、何时提问及如何判断结束 | 大模型结合目标、团队、已有结果和该 Prompt 决定后续行动 |
| 流程运行 | 某个团队依据具体版本的指令处理一个目标的实际过程 | 展示员工、任务、交付物、检查、阻塞、决策摘要与执行结果 |
| 交付物与问题 | 有来源和版本的需求、设计、代码、测试报告，以及检查意见、缺陷和处理结果 | 监督针对具体交付物；修改、修复后能够追溯复核依据 |
| 升级事项 | 员工拿不准的方案或问题，以及各级上级的评估情况 | 已确认按上下级升级；建议记录当前处理者、相关产物、候选方案、评估意见和用户决定 |

建议区分三种 Prompt：生成员工时用户输入的要求、生成后员工使用的工作指令、组织团队协作的流程指令。修改其中一种时，应展示影响，避免用户不知道实际改变了哪一层。

生成员工不代表其自动具备外部工具、账号或执行权限。所需能力与环境是否可用，应有可观察的检查结果；授权规则见待决事项 D-P03。

## 5. 用户工作闭环与界面职责建议

### SC-01 从一句组织目标到团队运行

1. 管理者描述需要什么团队、如何工作、做什么项目与交付什么结果。
2. 平台生成数字员工与协作流程草案，展示职责、工作 Prompt、协作关系、输入要求、所需工具和待澄清事项。
3. 管理者可以继续用 Prompt 调整员工和流程；员工和流程的启用、自主调整范围仍待细化，见 D-P02。
4. 大模型结合有效指令、项目上下文和实际产物分派工作，决定交接、检查、补充资料与返工。
5. 员工交付产物，其他员工按约定检查；发现问题后记录问题、责任、依据及修正后的复核结果。
6. 管理者查看目标、责任分工、当前进展、阻塞与需要自己决定的事项，并可提出修改、暂停或终止指令。
7. 完成时汇总实际交付、需求覆盖、代码与测试版本、缺陷、未验证项和待办；完成与交付接受的权限待决定。

任一环节出现员工拿不准的方案，进入 SC-05 的逐级升级路径。上级能够解决的问题在团队内处理；上级仍无法解决时继续升级，最终反馈用户。

建议界面围绕员工管理、团队与流程、项目运行、交付物与问题、管理者待办组织。聊天是表达目标和指令的入口，运行管理还需直接展示任务和结果，不能只要求用户阅读全部聊天记录才能判断进度。

### SC-02 员工和流程由 Prompt 持续调整

管理者可以描述“增加一位擅长某领域的员工”“让设计增加某项检查”“测试失败先定位再返工”等变化。平台说明生成或修改了什么，并记录版本。对正在运行的工作，需说明生效范围和受影响任务；立即变更、下次运行生效或团队自主改动均属于待决定事项。

### SC-03 项目需求变化

管理者提出新要求后，团队识别对需求、设计、代码和测试的影响，更新相关产物并重新组织必要评审。现有通过结论不能在没有影响判断的情况下直接套到修改后的产物上。

### SC-04 返工、分歧与恢复

| 触发情况 | 建议行为与用户可见结果 | 恢复或继续的出口 |
| --- | --- | --- |
| 员工定义或流程有歧义、缺少职责 | 指出具体缺口、冲突或缺失资料，保留草案状态 | 通过 Prompt 澄清和更新，明确后再安排受影响工作 |
| 工具不可用、执行失败 | 记录实际动作、结果和受影响任务，区别能力缺失与内容错误 | 在授权和约定限制内调整方式；拿不准处理方案时按 SC-05 向上级升级 |
| 监督发现问题 | 记录问题、产物版本、依据、责任和修正要求 | 大模型组织修正；针对新产物复核，保留历史失败及解决记录 |
| 员工互相认可，但真实测试失败 | 保留测试失败，不以互评文案覆盖实际结果 | 定位失败、修复和实际复测；未解决不能归为已验证通过 |
| 多个员工结论冲突或相互等待 | 展示各自依据和依赖，补充核查、重新安排或汇总争议 | 拿不准方案时按 SC-05 升级；不能把反复转交或等待显示为问题已解决 |
| 重复返工、没有进展或耗尽预算 | 展示尝试、剩余问题和已完成产物，不持续空转或自动改成通过 | 拿不准方案时按 SC-05 升级；具体限制和等待规则由 D-P06 细化 |
| 用户暂停或服务中断 | 区分已完成、未执行、正在执行和结果未知的动作 | 恢复时核实外部状态；保留已有成果，避免重复产生副作用 |

### SC-05 拿不准方案时逐级升级

**已确认的路径（U-05 / D19）：**

员工拿不准方案 → 提交上级评估 → 上级能解决则给出处理意见；仍无法解决则继续向上 → 最高层仍无法解决时反馈用户。

该路径适用于流程各环节，不能把“不确定”直接解释成已获授权自行选择。用户仍可主动介入；新增阶段审批和交付接受规则不由本决定推导。

**以下为使该路径可执行、可观察的产品建议，尚待细化：**

1. 升级时携带目标、具体问题、拿不准的原因、已有事实、相关产物版本、尝试过的方法及候选方案；上级能够补充核查并评估。
2. 界面显示当前由哪位上级处理、已经过哪些层级、各级意见和剩余问题。最终反馈用户时保留上述上下文，并明确需要用户回答什么。
3. 上级或用户给出处理意见后，记录决定来源和适用范围，再明确由谁执行及哪些任务恢复；补证、改方案或调整目标后的影响仍需检查。
4. 等待回复不能被当作认可或问题已解决。对依赖该决定的工作如何暂停、是否允许独立任务继续、提醒与超时处理，均见 D-P06，不在本次默认决定。
5. 层级未配置、无法找到上级或层级成环时，应显式暴露配置问题；如何修正和是否直接反馈用户仍待 D-P07 明确，不静默跳级或编造上级。

## 6. Prompt 驱动与大模型控制运行的含义

大模型根据流程 Prompt 和现场事实决定分工、下一步、交接、检查及返工，不把一套产品→设计→开发→测试的固定顺序写成所有团队必须遵守的流程。流程中是否有前置条件、并行分工、反复评审和动态补充员工，由有效规则与授权决定。

建议平台提供持久化运行状态、工具执行、事件记录、交付物版本、约定约束检查与暂停恢复能力。模型提出或选择下一步，实际结果由执行工具、产物和检查记录反馈；无效调用、执行失败和未知结果不能靠模型文案变成成功。

“可观察决策”指可核查的行动、依据摘要、关联产物和实际结果，不要求展示模型内部推理过程。采用何种调度框架、如何实现约束和恢复由系统设计师评估。

团队自主推进与上下级升级同时成立：大模型在明确规则内组织运行，拿不准方案时按 SC-05 提交上级评估。该升级机制不自动赋予上级改写员工、流程、用户目标或执行权限的权力。

## 7. 员工相互监督机制建议

1. **检查有对象**：每次检查对应具体需求、设计、代码或测试产物版本，并注明依据和结论。
2. **检查有后果**：发现问题能够影响交接和完成判断，并进入责任、修正、复核链路；监督的阻断权限见 D-P03。
3. **职责分离可辨识**：执行、评审和验证由哪些员工完成应可见；同一模型扮演不同员工不等于已经取得独立验证。
4. **真实证据保留**：需求和设计以可检查的条目与产物支撑；代码以实际变更、构建和运行支撑；测试以真实执行范围、结果、缺陷和复测支撑。
5. **变更需要影响判断**：旧版本的评审不能直接显示成新版本已通过；规则变更也应关联受影响的任务和结论。
6. **分歧可处理**：保留意见和证据，允许补证、重评和返工；员工拿不准方案时沿 SC-05 的上下级关系升级。相互监督关系与管理层级需要分别表达，监督者不因提出意见就自动成为被监督员工的上级。
7. **完成可核对**：团队报告完成时说明交付、覆盖、缺口和遗留问题；员工相互同意不单独证明软件可用或业务目标已满足。

相互监督是提高可靠性的机制，仍需用实际缺陷发现、修正和交付表现验证效果，不能承诺仅靠互评保证绝对正确。
